What if cloning a repo also cloned the person who knows it? A project can carry its own agent.

A seat lives in the repo next to the code: what it's for, where it may write, nothing else. Clone the project and the seat joins your residents by name, and your steward hands it the questions it knows. Birth a better one, send a pull request, and everyone who clones after you gets it too.

The story

Every coding assistant reads a project's README to learn it, and every one of them learns it again tomorrow. A project's knowledge should travel with the project: not as a document an assistant skims, but as a resident with a charter, a face, and a name, versioned in git beside the code it knows. Open source the project and the seat goes with it. Someone downstream births a better one and sends it back.

Three seat kinds, one roster. Seats the product ships (Pepper, Marco). Seats you birth for yourself (a voice, a working record). Seats a project carries in its repo. All three sit on the same roster, all three are reachable by anyone on it, and the steward routes on two fields: which project, and what the seat is for. Nothing else in the system knows the difference.

Rejected wording: "AI that understands your codebase", "repo-aware assistant", "context engine". Those describe reading. What is sold is a seat: a named agent with a scope, versioned with the code, that a community can improve by pull request.

What keeps it honest

This is the one scenario whose mechanism is designed and not built, and the card says so ("designed, not built") rather than hiding it. What is measured: the three seat kinds and the routing rule are written in SPEC_RESIDENTS §9 and verified by the resident who owns agent architecture; two residents on this machine already carry granted territory the way Ledger would; the roster is rendered into every prompt regardless of project; territory containment is enforced on canonical paths. The dependency is named: nothing here ships before GH#1010. Ledger and Tape are fiction; trade-lens is a real project on this machine with no seat yet.

RuleWhy
The merge is additive by construction Copying the card loader's precedence would hide Pepper the day the first project ships a seat.
Names are scoped per source: trade-lens/Ledger Two projects will both want a Reviewer. Bare name resolves when unique, refuses with the qualified forms when not — same grammar as GH#1190's persona/name.
A source key joins the index line "Pepper, for trade-lens, …" resolves on source + purpose without reading a charter. The key must sit where it cannot be mistaken for the address.
A project binding has a lifetime Delete the clone and the grant check returns false, which reads as "no grant" when the truth is "no seat". orphaned is a state the loader sets, not a deletion; re-clone restores it with its transcript.
The directory is .ilha/residents/, not a neutral name A neutral directory invites definitions with no birth rite behind them into a roster whose territory is operator-approved per seat.
No project-level charter floor A charter is what a seat is for; a floor would be the project asserting scope over an agent the operator birthed. Territory stays operator-approved.

What does not exist yet

Rejected, with reasons

ShapeWhy not
The seat's memory travels in the repo Memory is a transcript of one person's work, often private. The definition (a couple of KB) travels; the transcript stays under ~/.ilha.
Absolute folders in a project definition A PR'd seat cannot know where the next person clones. Relative, joined at load; the containment check runs unchanged on the result.
Delete the binding when the clone goes Loses the transcript's link for a directory that may come back tomorrow. Orphaned is visible and reversible.
Project seats reachable only from inside the project Reach is fleet-wide by design; a seat Pepper cannot reach is a card, not a resident.
