How it is sold

One moment a day. A moment is a question the visitor already has, answered by one thing ilha does, not a feature with a description under it. This scenario is one moment; the format it follows, and the other eleven, are in the teaser format study.

Where it runs

A static page picks the day's moment with no server, no cookie, no storage:

const day = Math.floor(Date.now() / 864e5);      // days since epoch, UTC

Same moment for every visitor that day, so two people who talk about it saw the same thing. UTC, so a "daily" teaser does not change while a group is looking at it. Twelve seats, so a 12-day cycle to start. The cycle lengthens as moments are added and no code changes. Growth is copy, not engineering.

What keeps it honest

A teaser makes a promise about the box. This one is honest on the day the checklist in part three is green and a stranger can run the story above on a fresh install. Until then it may run ahead of the release the way a film teaser does, but every line in it must point at something scheduled, never at the machine on one desk. part three

How it is built

Measured on origin/main. The delegation half exists; the door is one field earlier in the flow and one variant at the end of it.

drawn against: roster.json (12 seats) · asks.md (six-column ask anatomy) · engine/events.rs DeliveryReceipt + DeliveryState

What a stranger meets today

The ledger's own header says it is the only place that states current state. Measured, the state column reads like this:

| PA-001 | Separate agent traffic from his own | Marco | **engine half MERGED** — main 7c7548b7, #1044 closed
| PA-002 | FROTA says no ships while two are live | —     | **closed** — PR #1051, main 0b21cd1c
| PA-004 | porto-dock: verify, gate, file, dispatch | Marco | **CLOSED — MERGED ~03:0x, PR #1064**

The ask column is already in the operator's words — that half works. The state column is crew bookkeeping: a commit hash, an issue number, a PR. A stranger cannot tell from any of these whether the thing they asked for works now.

What she may say, and what she may not

StateShe saysNever
handed over Handed it to trade-lens. I'll tell you when it's fixed. Dispatched task 7 to sede 1787…

failed Couldn't do it: the data source needs a password I don't have. Task failed after 3 attempts, see logs

One rule generates the whole column: name the thing the stranger asked for, in the words they used, and say whether it works. Identifiers may follow an outcome as reference; they may never replace it.

The engine contract — one field earlier, one variant later

The delegation half already exists:

pub struct DeliveryReceipt {          // events.rs:48 — EXISTS
    pub id: String,
    pub delivery_key: Option, // a per-send retry key — NOT the ask's identity
    pub target: SessionRef,           // who it went to, typed: { session, label }
    pub status: DeliveryState,
    pub landed_at: DateTime,
}

pub enum DeliveryState {              // events.rs:77 — EXISTS
    Queued, Landed, Seen, Dismissed, Answered,
}                                     // ends at ANSWERED

Answered is a postal fact — the message reached a seat and the seat replied. It says nothing about whether the stranger's bug is fixed. Every state in that enum is about the envelope; the door needs a state about the work. And nothing on the wire says which ask a delivery serves: SessionRef names a session, not an ask.

The delta, in two places on the existing family:

// outbound — the delegation carries the ask's identity from the moment Pepper hands it over
ask_key: String             // PA-nnn — the ledger's durable key: assigned at open, never reused,
                            // never renumbered. The engine carries a key that exists; it mints none.

// settle — emitted by the seat that did the work
AskSettled {
    ask_key: String,        // joins this outcome to the ask it settles
    target: SessionRef,     // the typed ref DeliveryReceipt already carries
    outcome: AskOutcome,    // Done { what_changed } | Failed { why } | NeedsYou { question }
    settled_at: DateTime,
}                           // what_changed is in the SEAT's terms — it is the only party that knows

The receipt joins two facts held in two places. What was asked is Pepper's — it is already column 3 of asks.md, in the operator's words. What changed is the seat's — it is the only party that knows. Neither session can compose the whole sentence, so neither is asked to: the seat emits its half in AskSettled, the door reads the ask column by ask_key, and renders the two side by side. Nothing is translated twice, and nothing states what it does not know.

Rejected, with reasons

ShapeWhy not
Pepper picks the seat from a menu A stranger cannot choose between 12 charters they have not read. Choosing IS her job — a menu hands it back.
Show the live crew feed Measured on this machine: a single peer-opened turn carries 7–18 feed items. Ten minutes of that is the wall the hood study exists to remove.
Receipt links the PR A link to review is the work coming back. The receipt may carry it as reference under the outcome, never as the outcome.
Pepper writes the outcome text She would be inferring what changed from a transcript. The seat that did the work is the only honest author.
One session composes the whole receipt Pepper holds the phrasing and not the outcome; the seat holds the outcome and not the phrasing. Asking either for the sentence asks for a fact it does not have.
Mint the ask's identity at settle time Then the outcome cannot be joined to the ask. The key must travel outbound with the delegation — and the ledger already assigns one, so nothing new is minted.
No clarifying question — just route it the bug I saw yesterday has no referent for a fresh install with no history. One question is cheaper than one wrong delegation.

Checklist

  1. The ask's identity travels outbound. The delegation carries ask_key; a settle that names no open ask fails loud. [evidence: test — a delegation without an ask_key is refused; a settle with an unknown ask_key is refused]
  2. AskSettled on the existing family. One variant beside DeliveryReceipt, reusing SessionRef. [evidence: test — a settled ask round-trips through the wire with its key and outcome]
  3. The seat authors the outcome. Emitted by whoever did the work, never composed downstream. [evidence: test — an ask settled with no text from the seat renders "done, no detail given", never an inferred sentence]
  4. The door joins by ask_key. Ask column in the asker's words beside the outcome in the seat's words; neither half rewritten. [evidence: test — the rendered receipt contains both source strings verbatim]
  5. Handoff card, shared component. Seat, ask in the operator's words, one state line. Three clients render the same event. [evidence: test + screenshot at phone width]
  6. Identifier ban in the receipt path. A commit hash, PR or issue number may not be the outcome sentence. [evidence: test — a receipt whose outcome is only an identifier fails]
  7. The ledger gets a stranger view. Same six columns, state rendered from AskSettled rather than crew prose. [evidence: screenshot — the same three PA rows, readable by someone who has never seen the repo]
  8. Failure has a face. Failed and NeedsYou carry why, in the stranger's terms. [evidence: screenshot — the missing-password case]
